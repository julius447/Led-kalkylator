# LED-kalkylatorn — Fluent Snippets install (Chris)

**This is the WordPress/Bricks-native package.** Three files → three Fluent Snippets → paste one shortcode. No theme editing, no `wp-content` file uploads, no build step, no plugin. It is a **1-to-1 clone** of the prototype at https://julius447.github.io/Led-kalkylator/ — every font, weight, colour, gradient, spacing value and micro-interaction is byte-for-byte the same (the CSS and JS in these files are the prototype's files, unchanged; only the *packaging* differs).

> Why this exists: the earlier `HANDOVER.md` assumed a theme/plugin enqueue (`wp_enqueue_script`, `wp-content/themes/...`). You implement via **Fluent Snippets** instead, so here the exact same code is delivered as three paste-ready snippets. Follow this file; ignore the enqueue section of `HANDOVER.md`. (Everything else in `HANDOVER.md` — the data contract, formulas, worked example, GDPR, analytics — still applies and is the reference for *what the tool does*.)

## The three files

| File | Fluent Snippet type | Where it runs |
|------|--------------------|----------------|
| `1-ampy-led-styles.css` | **CSS** | Head — the calculator pages (or site-wide; it's scoped) |
| `2-ampy-led-scripts.js` | **JS** | Footer — the calculator pages |
| `3-ampy-led-shortcode.php` | **PHP** (Functions / PHP snippet) | **Everywhere — do NOT page-condition it** (the shortcode + REST route must register on every request) |

> **Rule of thumb for run conditions:** CSS + JS → the calculator pages only (keeps other pages lean; see the note in Step 2). PHP → everywhere. **One calculator per page** — don't place the shortcode twice on the same page (only the first would become interactive).

`1` and `2` are generated by pure concatenation of the prototype's untouched source files. `3` wraps the prototype's exact markup in a shortcode and adds an optional lead endpoint. Do not hand-edit `1` or `2`; if the tool ever changes, re-run `build-snippets.js` (see bottom).

## Install — 4 steps

### Step 1 — CSS snippet
Fluent Snippets → **New Snippet → CSS**. Title: `Ampy LED – CSS`. Paste **all** of `1-ampy-led-styles.css`. Save + Activate.

- **All component styling is scoped under `.ampy-calc`** and won't touch the theme. The file additionally sets **two global lines**: a Google-Fonts `@import` at the top (see the **Fonts / GDPR** note below) and, at the very bottom, the design-system base `html { font-size: 62.5%; }` (1rem = 10px) — the **same base your battery calculator already uses**. ampy.se already runs 62.5% globally, so that line changes nothing on your site.
- *Do not reorder the file.* The `@import` must stay the first rule (a style rule above it would silently stop the fonts loading), which is why the 62.5% base sits at the end.
- Simplest run condition: load this snippet on the **calculator pages** only (the base line is then page-scoped too). Loading it site-wide is also safe.

### Step 2 — JS snippet
Fluent Snippets → **New Snippet → JS**. Title: `Ampy LED – JS`. Paste **all** of `2-ampy-led-scripts.js`. Save + Activate.

- **Placement:** footer or header both work — set Fluent's position field to *"Before `</body>`" (footer)* if offered. The script self-initialises when the DOM is ready either way.
- **Run condition:** load it on the **calculator pages** only (same pages as the shortcode). It's harmless site-wide (it no-ops where there's no calculator), but scoping it keeps the ~50 KB off every other page and avoids a stray `led_calc_error` analytics event on non-calc pages.
- This is `data.js` + `engine.js` + `app.js` concatenated in that exact order (order matters). Don't reorder.

### Step 3 — PHP snippet
Fluent Snippets → **New Snippet → PHP / Functions**. Title: `Ampy LED – shortcode + endpoint`. Paste **all** of `3-ampy-led-shortcode.php` **(including the leading `<?php`)**. Save + Activate.

- Registers the shortcode `[ampy_led_kalkylator]` and the (optional) lead REST endpoint.
- **Leave this snippet running everywhere — do not page-condition it.** A shortcode and a REST route must be registered on every request (a shortcode conditioned off a page won't render there, and the `/wp-json` route must always exist). It outputs nothing on its own; the markup only appears where you place the shortcode.

### Step 4 — drop the shortcode on the page
In Bricks, add a **Shortcode** element (not a Code element) where the calculator should appear:

```
[ampy_led_kalkylator]
```

Per-page preset (loads the right segment/light-source/context automatically):

```
[ampy_led_kalkylator sida="belysning"]        → BRF / T8 / Snitt brinntid  (default)
[ampy_led_kalkylator sida="inomhusbelysning"] → Företag / T8 / Kontor
[ampy_led_kalkylator sida="utomhusbelysning"] → BRF / HPS / Garage
[ampy_led_kalkylator sida="spotlight"]        → Privat / GU10 / Snitt brinntid
[ampy_led_kalkylator sida="armaturer"]        → Företag / T8 / Lager
```

An unknown `sida` safely falls back to the BRF default. That's it — the calculator renders.

> **Why a Shortcode element, not a Code element:** a Bricks Code element HTML-escapes its content unless "Execute code" is enabled, and can render the markup as visible `<div…>` text. The shortcode route avoids that entirely.

## Leads — two options (pick one)

**Option A — mailto (default, zero backend).** Do nothing. On submit the form opens the visitor's mail client with the full lead pre-filled to `offert@ampy.se`. No lead is lost; nothing to host.

**Option B — capture server-side (recommended for volume/CRM).** In the **JS snippet (`2-ampy-led-scripts.js`)**, in the **`DEL 1/3 — DATALAGER`** block near the top (search the snippet for the string **`lead: { endpoint:`** — there is exactly one hit), find:

```js
lead: { endpoint: null, fallback_mailto: "offert@ampy.se" },
```

and set:

```js
lead: { endpoint: "/wp-json/ampy/v1/led-offert", fallback_mailto: "offert@ampy.se" },
```

The endpoint is already implemented in the PHP snippet (`3-...php`): same-origin `POST`, honeypot + per-IP rate limit + full server-side validation + mail-header-injection guard, e-mails `offert@ampy.se` (add your CRM push at the `TODO`). **The endpoint must stay same-origin** (a relative `/wp-json/...` path) — a cross-origin URL triggers a CORS preflight the route won't answer and every submit fails silently. Forward to an external CRM inside the PHP callback, never from the browser.

## Fonts / GDPR

The CSS snippet loads the three families via an `@import` from `fonts.googleapis.com` (kept verbatim from the prototype, so the render is 1-to-1). Two things to know — same as `HANDOVER.md` §9:

- A CSS `@import` is **render-blocking** and fetched after the stylesheet, so on a slow/blocked network the widget paints a moment late (it falls back to `system-ui`, then swaps in).
- It sends every visitor's IP to Google **before consent** — a real GDPR consideration for a consent-forward Swedish site.

**Clean fix (recommended, doesn't change the look):** download the three families as `woff2` (Plus Jakarta Sans 500/600/700, Outfit 400/500/600, JetBrains Mono 500/600/700), host them in WP Media or the theme, and replace the top `@import` line in the CSS snippet with local `@font-face { … font-display:swap }` rules. Then there are zero third-party calls. If you keep the `@import`, leave it exactly where it is (the first rule) — a style rule above it silently stops the fonts from loading.

- [ ] On the page, console: `getComputedStyle(document.documentElement).fontSize` returns **`"10px"`**. (If `"16px"`, the CSS snippet didn't load / was conditioned off the page.)
- [ ] BRF default shows **27 752 kr/år**, **16 819 kWh**, **7,8 ton**, **120 000 kr**, and the bar caption reads **"59 % mindre"**. (Proves data + engine are intact.)
- [ ] The type renders in **Plus Jakarta Sans** (headings) / **Outfit** (body) / **JetBrains Mono** (numbers) — not a system fallback. Quick check in console: `document.fonts.check('600 16px "Plus Jakarta Sans"')` → `true`. The result card is midnight `rgb(9,11,50)`, the CTA teal `rgb(0,169,145)`. *(These families load via the `@import`; see the Fonts / GDPR note if you self-host.)*
- [ ] Switch segments: Privat shows **no CO₂** (shows "Per månad / kr/mån"). The cost sub-line reads "· inkl installation" in every segment; only the unit differs (Privat "kr/ljuskälla", Företag/BRF "kr/armatur").
- [ ] Slider drags smoothly on a real iPhone (Safari) + Android; no page scroll while dragging; ticks tappable.
- [ ] Dropdown opens/groups/selects; tooltips show on a single tap and dismiss on Escape; consent checkbox is a visible box with a tick on the dark card.
- [ ] Lead form: name/e-post/phone/postcode/consent all required; junk phone/postcode rejected. Then per your choice — **(A)** submit opens a mail draft and the page does **not** navigate away; **(B)** a valid submit returns **200** and the thank-you shows.
- [ ] No horizontal scroll at 320 / 360 / 390 px; desktop two-column layout intact.

If the whole tool looks ~1.6× too big → the CSS snippet's `html{font-size:62.5%}` isn't applying on that page (check Step 1's run condition). That is the single most common issue and the only environmental dependency.

## Editing later (numbers, prices, copy)

All business data lives in the **DEL 1/3 — DATALAGER** block near the top of `2-ampy-led-scripts.js` (the `data.js` section). Change a price/watt/burn-hour/default there, re-save the JS snippet. The engine **validates** the data on load and shows the friendly error (not a blank widget) if a value is malformed. Never edit numbers in the engine block. After any change, the acceptance numbers above must still hold unless you changed the inputs that drive them.

## Regenerating the snippets (maintainers only)

These three files are **build artifacts**, generated from the prototype sources. They are self-contained — you do not need the sources or the generator to install. If you ever need to regenerate them (e.g. a number changes), do it in the repo, not from this ZIP: https://github.com/julius447/Led-kalkylator (`wordpress-fluent-snippets/build-snippets.js`, run `node build-snippets.js`). The build is deterministic — CSS/JS are pure concatenation of the sources, and the PHP embeds the prototype markup verbatim (only the `data-sida` value is templated + escaped) — so the output is identical every time.
